# Эксплуатация сайта IAML

Повседневная работа с уже развёрнутым сайтом (первое развёртывание — в [`DEPLOY.md`](DEPLOY.md)). Все команды
выполняются на сервере из каталога `/opt/iaml` пользователем, который состоит в группе `docker`.

## Шпаргалка

```bash
cd /opt/iaml
./deploy/status.sh                  # обзор: контейнеры, здоровье, размер базы, диск, последний бэкап, версия
./deploy/logs.sh                    # журнал приложения (Ctrl+C — выход);  logs.sh caddy | db | app --since 1h --no-follow
docker compose ps                   # состояние контейнеров
docker compose restart app          # перезапустить только приложение
docker compose stop                 # остановить всё (данные остаются)
docker compose up -d                # запустить всё / применить изменения в .env
./deploy/backup.sh                  # бэкап прямо сейчас
./deploy/update.sh                  # обновить сайт до последней версии
docker compose exec db sh -c 'exec psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'   # консоль SQL (выход: \q)
```

**Запрещено на рабочем сервере: `docker compose down -v`** — ключ `-v` удаляет тома, то есть базу данных, аватарки
и сертификаты. Обычный `docker compose down` данных не трогает.

## Что где хранится

| Что | Где | Как защищено |
|---|---|---|
| База данных: участники, новости, события, публикации, обсуждения, подписки, очередь писем, настройки | том Docker `iaml_pgdata` (в контейнере `/var/lib/postgresql/data`) | `deploy/backup.sh` (pg_dump) |
| Аватарки участников | том `iaml_uploads` (в контейнере `/data/uploads/avatars`) | `deploy/backup.sh` (tar) |
| Сертификаты HTTPS и учётная запись Let's Encrypt | том `iaml_caddy_data` | не входят в бэкап (выпускаются заново), но том **нельзя удалять**: лимиты Let's Encrypt |
| Настройки и секреты | `/opt/iaml/.env` (права 600) | только вручную: менеджер паролей |
| Код и страницы сайта | `/opt/iaml` (git-репозиторий) | GitHub |
| Резервные копии | `/opt/iaml/backups/iaml-ГГГГММДД-ЧЧММСС/` | копируйте за пределы сервера |
| Журналы | Docker (json-file), на каждый контейнер до 5 файлов по 10 МБ | ротация автоматическая |

Тома можно увидеть командой `docker volume ls` (имена начинаются с `iaml_`). Наружу (в интернет) открыты только порты 80 и 443
контейнера Caddy; база данных и приложение доступны только внутри сети Docker.

## Обновление

```bash
cd /opt/iaml
./deploy/update.sh
```

Что делает скрипт:

1. проверяет, что в отслеживаемых файлах нет локальных правок (настройки живут в `.env`, git его игнорирует);
2. **делает бэкап** (`backups/iaml-…-pre-update`) — миграции базы применяются автоматически при старте;
3. `git pull --ff-only`;
4. пересобирает образ (`docker compose build --pull` — заодно подтягиваются обновления безопасности базовых образов);
5. перезапускает контейнеры (`docker compose up -d`);
6. ждёт, пока приложение станет `healthy` (до 3 минут); при неудаче печатает последние строки журнала и команду отката;
7. печатает версии «было → стало» и состояние контейнеров.

Простой сайта во время обновления — несколько секунд; Caddy сам повторяет запросы до 10 секунд, поэтому посетители обычно
ничего не замечают, а при более долгой паузе видят страницу «The site is restarting».

Параметры: `--no-backup` (не делать бэкап — не рекомендуется), `--no-pull` (только пересобрать текущую версию, например чтобы
получить обновления базовых образов), `--no-prune` (не удалять старые образы), `--ref ВЕТКА_ТЕГ_ИЛИ_КОММИТ` (см. «Откат»).

Как часто: при выходе новой версии сайта и **не реже раза в месяц** (`./deploy/update.sh --no-pull` тоже подойдёт) — так
вы получаете исправления безопасности Node.js, PostgreSQL и Caddy. Узнать, что вышла новая версия:

```bash
git fetch && git log HEAD..origin/main --oneline
```

## Откат

Каждое обновление в конце печатает «previous version: `abc1234`» и готовую команду отката. Вернуться на прежнюю версию кода:

```bash
./deploy/update.sh --ref abc1234        # бэкап → переключение на этот коммит → пересборка → запуск
./deploy/update.sh --ref main           # потом — снова на последнюю версию
```

(пока выбран конкретный коммит, обычный `./deploy/update.sh` откажется работать и подскажет команду `--ref main`).

**Если новая версия успела изменить базу данных** (в ней были новые миграции), откат кода миграции не отменяет. Старый код
обычно продолжает работать с новыми таблицами, но если нет — верните и данные из бэкапа, сделанного перед обновлением:

```bash
./deploy/update.sh --ref abc1234 --no-backup
./deploy/restore.sh backups/iaml-ГГГГММДД-ЧЧММСС-pre-update
```

Всё, что появилось после этого бэкапа (регистрации, сообщения, посты), при восстановлении пропадёт.

## Резервные копии

`./deploy/backup.sh` создаёт каталог `backups/iaml-ГГГГММДД-ЧЧММСС/` (время UTC):

| Файл | Содержимое |
|---|---|
| `db.dump` | вся база данных (`pg_dump -Fc`, сжатый формат); скрипт проверяет, что файл читается |
| `uploads.tar.gz` | аватарки |
| `MANIFEST.txt` | время, версия кода, размеры, число миграций и пользователей |

По умолчанию хранятся **последние 14 копий**, более старые удаляются (`--keep 30` или `BACKUP_KEEP=30` — иначе). Неудавшийся бэкап не
оставляет «полуготовых» файлов, а скрипт завершается с ошибкой (код ≠ 0). Каталог `backups/` закрыт для всех, кроме вашего
пользователя (права 700), и содержит собственный `.gitignore`, поэтому в git не попадёт.

**Ночной бэкап по cron.** Сначала один раз запустите `./deploy/backup.sh` вручную (он создаст каталог `backups/`), затем:

```bash
crontab -e
```

и добавьте строку (каждую ночь в 03:15 по времени сервера, журнал — в `backups/backup.log`):

```
15 3 * * * cd /opt/iaml && ./deploy/backup.sh >> backups/backup.log 2>&1
```

**Копия за пределами сервера — обязательна.** Бэкап на том же диске не спасёт при потере сервера или аккаунта у провайдера.
Варианты:

* С **другого** компьютера или сервера забирайте копии по расписанию: `rsync -az deploy@IP_СЕРВЕРА:/opt/iaml/backups/ ~/iaml-backups/`
  (так взломанный веб-сервер не сможет стереть внешние копии, если у него нет доступа к вашей машине). Без `--delete` внешняя папка
  накапливает копии дольше, чем на сервере, — удаляйте старые сами; с `--delete` она повторяет серверную ротацию.
* Облачное хранилище через `rclone` (S3, Backblaze B2, Google Drive, Яндекс Диск и т. д.), лучше с шифрованием (`rclone crypt`).
* Снимки (snapshots) сервера у провайдера — как дополнение.

В копиях лежат **персональные данные** (e-mail, имена, места работы): храните их в зашифрованном виде и не раздавайте.
Раз в месяц проверяйте, что внешняя копия свежая (`ls -lt /opt/iaml/backups | head`, `tail backups/backup.log`).

**Что в бэкап не входит:** файл `.env` (храните его отдельно в менеджере паролей), сертификаты (выпускаются заново), образы Docker.

### Восстановление

```bash
cd /opt/iaml
./deploy/restore.sh                                   # покажет список бэкапов
./deploy/restore.sh backups/iaml-20261001-031500      # восстановить выбранный
```

Скрипт заменяет **всё** содержимое базы и аватарок содержимым бэкапа. Он: просит ввести слово `RESTORE`; делает страховочную
копию текущего состояния (`…-pre-restore`; пропустить — `--no-safety-backup`, если стенд сломан); останавливает приложение;
пересоздаёт базу из дампа; заменяет аватарки; запускает приложение и ждёт, пока оно станет `healthy`. Отдельные файлы:
`./deploy/restore.sh --db db.dump --uploads uploads.tar.gz`.

### Учения по восстановлению (раз в квартал)

Бэкап, который ни разу не восстанавливали, — это надежда, а не бэкап. Проверьте на своём компьютере с Docker (на рабочем сервере
этого делать не нужно):

```bash
git clone https://github.com/viptdv333-boop/IAML.git iaml-drill && cd iaml-drill
./deploy/gen-env.sh --local
export COMPOSE_PATH_SEPARATOR=: COMPOSE_FILE=docker-compose.yml:docker-compose.local.yml COMPOSE_ENV_FILES=deploy/local.env
docker compose up -d --build
./deploy/restore.sh --yes --no-safety-backup /путь/к/iaml-20261001-031500
curl http://localhost:18080/api/health                # здоров?
./deploy/status.sh                                    # число пользователей совпадает с рабочим сайтом? (см. MANIFEST.txt)
docker compose down -v --remove-orphans               # убрать учебный стенд (это локальный стенд, здесь -v уместен)
```

### Потеря сервера: восстановление на новом

1. Шаги 1–5 из `DEPLOY.md` (новый VPS, защита, Docker, `git clone`).
2. Положите на сервер `/opt/iaml/.env` из менеджера паролей (если создадите новые секреты — старые ссылки «отписаться» в разосланных
   письмах перестанут работать; больше ничего не пострадает) и сделайте `chmod 600 .env`.
3. Скопируйте нужный бэкап из внешнего хранилища в `/opt/iaml/backups/`.
4. `docker compose up -d --build`, затем `./deploy/restore.sh --no-safety-backup backups/iaml-…`.
5. Переключите DNS-запись (A) на новый IP; Caddy выпустит сертификат, как только имя начнёт указывать на сервер.

## Журналы

```bash
./deploy/logs.sh                         # приложение (по умолчанию)
./deploy/logs.sh caddy                   # веб-сервер: выпуск сертификатов, ошибки, access-журнал
./deploy/logs.sh db                      # PostgreSQL
./deploy/logs.sh app --since 2h --no-follow | grep -i error
```

* Приложение пишет по одному JSON-событию в строке; строки запросов без параметров (токены в URL не пишутся), cookie и заголовки
  авторизации скрыты.
* Access-журнал Caddy — тоже JSON: метод, путь (без `?…`), статус, время, IP клиента. IP-адреса — персональные данные: срок их
  хранения ограничен ротацией (5 файлов по 10 МБ на контейнер — от нескольких дней до пары недель).
* Ротация настроена в `docker-compose.yml` (`json-file`, `max-size: 10m`, `max-file: 5`): диск журналами не заполнится.
* Каждые 30 секунд в журнале приложения появляется запрос `/api/health` — это проверка здоровья контейнера, не посетитель.

## Мониторинг

1. **Внешняя проверка доступности** (главное). Заведите бесплатный монитор (UptimeRobot, Better Stack, Uptime Kuma, Healthchecks
   и т. п.) на `https://ВАШ_ДОМЕН/api/health`: интервал 1–5 минут, условие — код 200 и слово `"ok":true` в ответе. Этот адрес
   проверяет сразу Caddy, приложение и базу данных. Оповещения — на e-mail или в Telegram **не на ящик этого же сайта**. Включите также
   предупреждение об истечении сертификата, если сервис это умеет (Caddy продлевает его сам за ~30 дней).
2. **Диск.** Раз в месяц: `df -h /` и `docker system df`. Если занято больше 80 % — удалите старые образы (`docker image prune`), лишние
   бэкапы, уменьшите `--keep`. Включите оповещения о диске и памяти в панели провайдера, если есть.
3. **Очередь писем.** В админке (статистика / раздел Mail queue) следите за числом `failed`: письмо становится `failed` после 8
   неудачных попыток. Причины — в `last_error` (см. «Если что-то не работает» в `DEPLOY.md`).
4. **Бэкапы.** Свежий каталог в `backups/` и пустой хвост `backups/backup.log` без ошибок.
5. **Обзор.** `./deploy/status.sh` — раз в неделю.

## Секреты и пароли

| Секрет | Где | Когда менять |
|---|---|---|
| `SESSION_SECRET` | `.env` | только при утечке |
| `RESEND_API_KEY` | `.env`, панель Resend | при утечке, смене сотрудника, раз в год |
| `POSTGRES_PASSWORD` | `.env` + внутри базы | при утечке |
| пароли администраторов | страница аккаунта | при подозрении, при уходе администратора |
| SSH-ключи, пароли GitHub / регистратора / Resend / хостинга | — | включите двухфакторную защиту |

### `SESSION_SECRET`

Это ключ подписи (HMAC) одноразовых кодов подтверждения и ссылок «отписаться» в письмах. Что произойдёт при замене:

* все **неиспользованные коды** (живут 15 минут) станут недействительными — пользователям придётся запросить код заново;
* все **ссылки «отписаться»** в уже разосланных письмах Mongolist перестанут работать (у них нет срока действия) — подписчики смогут
  отписаться на странице своего аккаунта;
* сессии входа (cookie) **не затрагиваются**.

Поэтому меняйте секрет только при подозрении на утечку:

```bash
cd /opt/iaml
openssl rand -hex 32                    # скопируйте результат
nano .env                               # подставьте в SESSION_SECRET=
docker compose up -d                    # приложение пересоздастся с новым секретом
```

### `RESEND_API_KEY`

1. В Resend создайте **новый** ключ (Sending access) для вашего домена.
2. `nano .env` → замените `RESEND_API_KEY=` → `docker compose up -d`.
3. Проверьте отправку (например, форма контактов или повторная отправка письма из Mail queue).
4. Удалите старый ключ в панели Resend.

Письма, ожидавшие в очереди, уйдут уже с новым ключом.

### Смена пароля базы данных

PostgreSQL запоминает пароль **один раз** — при создании тома. Поэтому правка `POSTGRES_PASSWORD` только в `.env` сломает
подключение приложения (`password authentication failed`). Правильный порядок:

```bash
cd /opt/iaml
docker compose exec db sh -c 'exec psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
#   ALTER USER iaml WITH PASSWORD 'новый_пароль_латиницей_и_цифрами';        (имя — значение POSTGRES_USER, по умолчанию iaml)
#   \q
nano .env                               # POSTGRES_PASSWORD=новый_пароль_латиницей_и_цифрами
docker compose up -d
```

Если вы уже изменили `.env` и приложение не стартует, верните в `.env` прежний пароль, выполните `docker compose up -d`, а затем
повторите процедуру выше.

### Забытый пароль администратора

`./deploy/create-admin.sh --email admin@example.org --password 'новый-пароль'` — для существующей учётной записи пароль
заменяется (и она становится администратором, если не была). Сразу после входа смените пароль на свой.

## Миграции базы данных

* Изменения структуры базы — это SQL-файлы `backend/migrations/NNN_название.sql`. Приложение применяет **новые** файлы по порядку
  автоматически при каждом старте (`MIGRATE_ON_START=true`), каждый — в своей транзакции, с защитой от одновременного запуска.
  Применённые файлы записываются в таблицу `schema_migrations` вместе с контрольной суммой.
* **Применённую миграцию редактировать нельзя.** Если файл изменился, приложение откажется стартовать с сообщением
  `Migration … was modified after it was applied`. Любое изменение схемы — это новый файл с следующим номером.
* Перед каждым обновлением `update.sh` делает бэкап именно на случай неудачной миграции.
* Начальные данные (участники, меню, категории ссылок) загружаются **один раз**; повторный запуск приложения их не восстанавливает, поэтому
  удалённое вами в админке не «воскреснет». Принудительная перезагрузка (`docker compose exec app node scripts/seed.js --force`) вернёт
  исходные записи — используйте только осознанно. Демо-данные (`seed:demo`) на рабочем сервере не загружаются никогда.
* Версия PostgreSQL закреплена на **16** (`postgres:16-bookworm`): мелкие обновления ставятся сами, а переход на 17 и выше
  выполняется только через дамп и восстановление (`backup.sh`, новый том, `restore.sh`) — не меняйте номер версии в
  `docker-compose.yml` «на лету».

## Персональные данные

Что хранит сайт: e-mail, имя, место работы, хэш пароля (scrypt), необязательную аватарку, время последнего входа, подписки на Mongolist,
сообщения форм, записи журнала действий администраторов; в журналах контейнеров — IP-адреса. E-mail и место работы **не публичны**:
видны только администраторам.

* **Удаление аккаунта.** Участник может удалить аккаунт сам (страница аккаунта); администратор — в разделе пользователей. Данные
  аккаунта удаляются, сообщения в Discuss остаются как «Deleted user».
* **Бэкапы содержат персональные данные**, в том числе удалённых позже аккаунтов, пока бэкап не будет вытеснен ротацией
  (по умолчанию 14 копий ≈ две недели). Храните бэкапы зашифрованными, доступ ограничьте; при запросе на удаление данных учитывайте этот срок.
* Очередь исходящих писем чистится приложением автоматически (отправленные и неудавшиеся письма старше 30 дней удаляются, коды
  подтверждения стираются после доставки).
* Экспорт подписчиков Mongolist (CSV) есть в админке.
* Resend обрабатывает адреса получателей и тексты писем; выберите регион, соответствующий вашим требованиям, и укажите это в
  странице `privacy.html`.

Это справочная информация, а не юридическая консультация: тексты `privacy.html` и `terms.html` согласуйте с юристом организации.

| Сертификаты Let's Encrypt | бесплатно |
| Resend, бесплатный тариф | 0: до 3 000 писем в месяц и 100 в сутки |
| Resend, платный тариф | по потребности, если подписчиков и рассылок станет больше лимитов |
| Внешнее хранилище для бэкапов | 0–5 € в месяц (объём бэкапов — единицы и десятки мегабайт) |

Итого: порядка 5–10 € в месяц плюс домен. Лимит Resend по частоте запросов приложение соблюдает само: письма уходят по одному с
паузой `MAIL_MIN_INTERVAL_MS` (по умолчанию 600 мс).

## Чек-лист безопасности

- [ ] Вход на сервер только по SSH-ключу, `PasswordAuthentication no`, `PermitRootLogin no` (шаг 3 `DEPLOY.md`).
- [ ] Брандмауэр ufw включён: открыты только 22, 80, 443 (tcp) и 443 (udp). Порты базы данных и приложения **не публикуются** в Docker.
- [ ] Автообновления безопасности ОС включены (`unattended-upgrades`); раз в месяц — `./deploy/update.sh`.
- [ ] `.env` имеет права 600 (`ls -l .env`), не попадает в git, его копия хранится в менеджере паролей.
- [ ] Бэкапы делаются ежедневно, копия лежит вне сервера в зашифрованном виде, восстановление проверено (учения).
- [ ] Двухфакторная аутентификация включена в аккаунтах GitHub, Resend, регистратора домена и хостинг-провайдера.
- [ ] Администраторов столько, сколько нужно (разделы пользователей в админке); пароли уникальные и длинные.
- [ ] Внешний монитор `/api/health` настроен, оповещения доходят.
- [ ] Не используйте `docker compose down -v`; не правьте применённые миграции; не добавляйте `ports:` для `db` и `app`.
- [ ] Доступ специалиста — отдельным пользователем с его собственным SSH-ключом; после окончания работ ключ удаляется из
  `~/.ssh/authorized_keys`, а `RESEND_API_KEY` и пароли, которые он видел, заменяются.

Примечание: приложение подключается к базе под владельцем кластера внутри контейнера, а сама база доступна только из внутренней сети
Docker без доступа в интернет — снаружи до неё не добраться.

## Типовые задачи

**Добавить администратора:** `./deploy/create-admin.sh --email new@example.org --first Имя --last Фамилия` (если учётная запись уже
есть, она станет администратором; новый пароль будет напечатан только для новой записи).

**Включить перенаправление www → домен:** создайте A-запись для `www`, добавьте в `.env` строку `WWW_HOST=www.ВАШ_ДОМЕН`, затем `docker compose up -d`.

**Сменить домен:** подтвердите новый домен в Resend, в `.env` поменяйте `DOMAIN` (и `MAIL_FROM`), переключите DNS на сервер, `docker compose up -d`.

**Плановые работы:** `docker compose stop app` — посетители увидят страницу «The site is restarting» (код 503), а внешний монитор пришлёт
оповещение (приостановите его на время работ); вернуть сайт: `docker compose start app`.

**Перенос на другой сервер:** сделайте бэкап и скопируйте его; на новом сервере выполните шаги 1–8 из `DEPLOY.md` и `./deploy/restore.sh`;
переключите DNS; старый сервер удалите после проверки.

**Применить изменённый `Caddyfile`:** `docker compose restart caddy`. Правки в отслеживаемых файлах (включая `deploy/Caddyfile`) блокируют
`update.sh`; для постоянных настроек используйте `.env`. Для проверки Let's Encrypt без риска упереться в лимиты временно добавьте в начало
глобального блока `deploy/Caddyfile` строку `acme_ca https://acme-staging-v02.api.letsencrypt.org/directory` (тестовые сертификаты браузеры не
признают), перезапустите Caddy, а после проверки верните файл командой `git checkout deploy/Caddyfile` и снова `docker compose restart caddy` —
Caddy сам получит настоящий сертификат. Том `iaml_caddy_data` при этом удалять не нужно.

**Посмотреть расход ресурсов:** `docker stats --no-stream` (потолки памяти — `APP_MEM_LIMIT`, `DB_MEM_LIMIT`, `CADDY_MEM_LIMIT` в `.env`).

**Если сайт «лёг» ночью:** `./deploy/status.sh` → `docker compose ps` → `./deploy/logs.sh app --since 6h --no-follow | tail -100` →
`./deploy/logs.sh caddy --since 6h --no-follow | tail -50`. Контейнеры перезапускаются сами (`restart: unless-stopped`), поэтому чаще
всего достаточно причины в журнале. Не освобождается память — увеличьте сервер или `APP_MEM_LIMIT`.
